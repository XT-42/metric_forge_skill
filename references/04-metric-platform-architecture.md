# 指标平台架构设计参考

本文汇总指标平台的技术架构设计思路，主要以快手 OneMetric + OneService 的四层架构为主线（细节最完整、公开分享中给出的图示最清楚），并结合美团指标平台的"自动语义 + 增强计算"作为进阶参考。如果只是要做一个中小规模的指标平台，读到"第2节：四层架构"和"第4节：查询与执行"基本够用；美团那套自动化建模/物化能力（第5节）适合指标规模到万级以上再考虑。

## 1. 总体设计思路

指标平台要解决的本质问题是把"指标语言"翻译成"技术语言"：业务方说的是"电商本周各地域母婴产品支付订单金额"，系统需要的是能在 Hive/Druid/HBase 等引擎上跑的 SQL 或查询计划。中间这层翻译能力，就是指标平台存在的意义。

```
指标/维度（面向业务）→ OneService（指标语言 → 技术语言：执行计划 + 语言翻译 + 二次计算）→ 存储/计算（KV/OLAP/DFS，Spark/Mr/Presto）
```

## 2. 四层架构

快手把整套系统拆成 OneMetric（统一指标管理）+ OneService（统一服务）两大子系统，共四层：

```
┌─────────────────────────────────────────┐
│ 服务层：元数据服务 + 查询服务（对外统一走 OneDSL：数据集+指标+维度）│  ─┐
├─────────────────────────────────────────┤   OneService
│ 引擎层：查询引擎 + OneSQL（DSL → SQL 翻译）              │  ─┘  统一服务
├─────────────────────────────────────────┤
│ 模型层：模型构建 + 模型搜索                              │  ─┐
├─────────────────────────────────────────┤   OneMetric
│ 元数据层：指标/维度管理 + 表管理 + 数据集管理               │  ─┘  统一指标管理
└─────────────────────────────────────────┘
        （右侧贯穿一条"指标一致性"校验模块，覆盖模型层和元数据层）
```

**为什么要分成"指标管理"和"服务"两大块，而不是一个系统？** 因为两者的关注点完全不同：指标管理关心的是"这个指标定义得对不对、规不规范"，是治理问题；服务关心的是"这个查询能不能快速返回、稳不稳定"，是工程问题。分开设计可以让两边的迭代节奏互不干扰——治理规则可以按季度迭代，查询引擎性能优化可以按周迭代。

### 元数据层：三类核心资产
- **指标/维度管理**：存储指标和维度的逻辑定义（业务口径）+ 物理定义（技术口径：聚合类型、过滤条件等）。
- **表管理**：记录物理表的元信息（哪张表、哪些字段对应哪些指标/维度）。
- **数据集管理**：把指标+维度+表组合成一个可直接查询的数据集单元，是模型层和服务层之间的桥梁。

### 模型层：模型构建 + 模型搜索
这是整个架构里最有技术含量的一层，展开讲见第 3、第 4 节。

## 3. 模型构建：四种数据模型

维度建模的四种经典模型类型，指标平台需要支持自动或半自动构建这几类模型：

| 模型类型 | 结构 | 适用场景 |
|---|---|---|
| 单例模型 | 只有事实表，没有关联维表 | 指标和维度都在一张宽表里，最简单 |
| 星型模型 | 一张事实表 + 多张一度关联的维表 | 最常见，维表不再向外关联 |
| 雪花模型 | 事实表 + 维表，维表继续向外关联更多维表 | 维度需要多层下钻（如商家→品牌、商家→蜂窝） |
| 星座模型 | 多张事实表共享维表 | 需要跨多个业务过程联合分析（如同时看订单和退款） |

美团的实践给出了一个重要提醒：**从雪花模型出发穷举构建星座模型存在组合爆炸风险**——如果有 N 个雪花模型两两/三三组合，数目会呈阶乘级增长，而且大多数组合对实际查询毫无意义。工程上更优的做法是不提前穷举，而是"按需构建"：只记录各个成分指标各自的雪花模型（半成品星座模型），等到真正有查询请求时，根据查询条件先淘汰不匹配的雪花模型，再做组合——大幅减少需要维护的模型数量。这一条对任何要做自动建模的团队都值得参考，不要一开始就设计成"提前算好所有可能组合"。

## 4. 模型搜索/路由：一个查询该用哪张表

同一个指标往往会被物化/沉淀在多张表里（不同的加工粒度、不同的时效），指标平台需要自动为一次查询选出最合适的表。快手给出的两阶段策略：

**筛选阶段**（逐步淘汰不匹配的表）：
1. 指标筛选：淘汰指标不匹配的表
2. 维度筛选：淘汰维度不匹配的表
3. 范围筛选：淘汰数据范围（行）不匹配的表
4. 日期筛选：淘汰数据日期范围不满足的表

**排序阶段**（在剩下的候选表里选最优）：
1. 生产排序：取早不取晚，优先选早生产完成的表
2. 效率排序：取快不取慢、取全不取缺，优先选满足更多字段的表
3. 维度排序：取粗不取细，优先选行数少的表（细粒度表查询更慢）
4. 手动排序：自定义优先级，人工兜底

美团的路由机制更复杂一些，多了一层"指标高亮"（用户点选一个指标/维度后，系统实时计算哪些其他指标维度还能一起分析，能的高亮可选、不能的置灰），以及九条模型匹配规则（数据范围判定、引擎范围判定、强制维度判定、GroupingSets 维度组判定、模型标签或动态范围、分区策略判定、SQL 模型判定、多语言环境判定、维度集合判定）。如果指标平台要支持交互式的自助分析工具（而不只是固定报表取数），美团这套"先高亮引导、后路由选表"的思路值得参考；如果只是服务固定报表和 API 取数，快手的四步筛选+四步排序已经足够。

## 5. 查询语言设计：DSL 五要素

不管底层引擎多复杂，对外暴露的查询语言应该尽量简单、贴近业务表达。快手把一个自然语言查询需求（"电商本周各地域母婴产品支付订单金额"）拆解为固定的五要素：

| 要素 | 对应查询需求中的部分 | 示例 |
|---|---|---|
| 数据集 | 圈定查询范围 | 电商 |
| 时间范围 | 统计的时间区间 | 本周 = [20201019-20201025] |
| 维度 | 按什么切分 | 各地域 → 维度=[地域] |
| 过滤条件 | 筛选限定 | 母婴产品 → 过滤条件=[商品二级类目=母婴产品] |
| 指标 | 要统计的量 | 支付订单金额 |

用 JSON/DSL 表达时大致是 `{query_type, dataSource, filter, dim, metric, intervals, engine}` 这样的结构。设计 DSL 时的原则是：**DSL 描述的是"要什么"（意图），而不是"怎么算"（实现）**——怎么算（选哪张表、怎么 JOIN、走哪个引擎）应该由模型搜索和执行计划自动完成，不需要调用方关心。

## 6. 执行计划与 SQL 翻译

从 DSL 到最终执行，中间要经过：

```
DSL → 语义拆分（同环比、占比等） → 引擎拆分（按 Hive/Druid/Get/Scan 等引擎类型拆分成多个 Query）
   → 每个 Query 生成 AST 树 → 基于 RBO（基于规则的优化器）优化 AST 树 → 生成 SQL/查询语句
   → 提交到对应引擎执行 → 结果通过 Spark/Local 做二次计算（多引擎结果合并、跨源 JOIN）→ 返回数据
```

其中 SQL 翻译（快手叫 OneSQL）的核心是"模型查询编译器"：输入是查询请求（数据集+维度+指标+时间范围）和模型定义（事实表+维表的关联关系），输出是一棵 AST（Select Statement 套 From/Where/Join/Group 等子节点），再经"查询转化器"生成最终可执行的 SQL，方言适配到 Hive/Druid/HBase 等不同引擎。这一层的价值在于让上层完全不用关心底层引擎的 SQL 方言差异。

**一个 Job 会被拆成多个 Task（按语义拆分，比如同环比会拆成"本期"和"同期"两个子任务），每个 Task 又会被拆成多个 Query（按引擎类型拆分），最终多个 Query 的结果需要在 Spark/Local 层做二次计算合并**——这个"Job → Task → Query → 二次计算"的拆分粒度设计，是支持跨源查询（同时查 Hive 和 Druid 的数据再 JOIN 到一起）的关键，值得在架构设计文档里画出来。

## 7. 性能与稳定性：进阶能力（美团实践）

如果指标平台已经有一定规模（模型/指标到万级以上），可以参考美团的两类进阶能力：

- **查询降级策略**：
  - 同源降级：模型物理存储不变，切换查询引擎，由查询服务自动适配 SQL 方言。
  - 异构降级：切换到另一份物理模型（比如从明细表降级到预聚合表），系统屏蔽查询细节差异。
  - 场景：最优模型查询失败或超时未返回时，自动降级到次优方案，提升查询成功率而不是直接报错。

- **智能物化**：
  - 数据集物化（用户主动发起）：轻度聚合物化（只物化选中的指标依赖，保留上卷下钻能力）或结果物化（直接固化计算结果，适合维度组合固定的场景，如构建 GroupingSets 表）。
  - 全局物化（系统自动触发）：根据查询热度、行为分析自动构建最优模型，注册回指标仓库供后续查询复用。

这两类能力本质上都是"空间换时间"，核心价值是把复杂查询的计算成本从"查询时实时计算"挪到"提前批量计算好"，代价是需要额外的存储和调度资源，只有查询量/复杂度到了一定规模才划算。

## 8. 从零开始搭建的建议优先级

如果是从零搭建，不要一次性对齐美团/快手的完整架构，按以下优先级递进：

1. **先做元数据层**：指标/维度的逻辑+物理定义能被结构化存储和查询，哪怕还没有自动化查询引擎，光是有一个"查得到定义"的系统就已经解决了"文档化管理"阶段的大部分问题。
2. **再做统一查询接口**：哪怕内部实现是人工维护的固定 SQL 模板，也要让下游统一走一个服务层查数据，而不是各自连 Hive/OLAP。这一步解决"改了不生效"的问题。
3. **然后做模型自动关联+路由**：当指标和表的数量涨到人工维护关联关系开始吃力时（通常是几十到上百张表的量级），再投入做自动建模和模型搜索。
4. **最后做智能物化/降级等性能优化**：查询量真正上规模、遇到明显的性能/成本瓶颈时再做，过早优化是浪费。
