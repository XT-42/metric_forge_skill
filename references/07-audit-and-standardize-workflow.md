# 模式一：存量指标盘点与规范化

对应 skill 的第一个实战能力——拿到企业一堆散落的历史指标（可能来自旧报表、Excel、PPT截图、口头描述），把它们清洗成一份规范化、去重、有编号的指标资产清单，交付形式默认是一份自包含的 HTML 交互台账（`assets/html-templates/metric-audit-table.html`），也可以按用户要求改产 Excel。

## 1. 触发场景

用户说"帮我理一下我们现在的指标"、"这些报表里的指标口径好像有点乱"、"帮我做一份指标盘点"、上传了报表/文档/截图并要求梳理指标，都进入这个工作流。

## 2. 输入：怎么从用户材料里提取原始指标

用户提供的材料形式多种多样，处理原则：
- **结构化文件**（Excel/CSV 报表导出、已有的指标文档）：直接读取列名、表头、字段说明，每个字段/列都可能对应一个候选指标。
- **非结构化文档**（PDF/Word 报告、PPT 截图）：通读全文，把出现的数值型概念（"XX率""XX量""XX数""XX金额""XX时长"）都提取为候选条目，同时记录它出现的上下文（哪张表、哪句话），这段上下文很重要，后面判断口径冲突要用。
- **口头列举**（用户直接在对话里说"我们现在有活跃用户数、GMV、转化率……"）：逐条记录，主动追问不清楚的地方（这个转化率的分子分母是什么、GMV 是否含退款）而不是自己猜。

**每条候选指标都要记录来源**（哪份文档/哪张表/第几页），这是后面判断"同名不同义"还是"确实是同一个指标只是名字不同"的关键证据——来源不同、口径描述不同的两条同名记录，大概率是冲突；来源不同但口径描述完全一致的，大概率是重复记录，直接合并。

## 3. 共享指标数据结构

三个模式（盘点、新增、框架图）共用同一套字段结构，方便互相喂数据。做盘点产出的每条记录，字段如下（对应 HTML 模板 `METRICS` 数组里的对象结构）：

```json
{
  "id": "TRXN_G_00010000",
  "name_cn": "支付成功订单数",
  "name_en": "paid_order_cnt",
  "type": "原子指标",
  "domain": "交易域",
  "level_asset": "A1",
  "level_security": "C2",
  "status": "normalized",
  "conflict_note": "",
  "analysis": ["衡量核心交易转化结果规模", "作为公司级经营看板核心指标"],
  "rules": ["仅统计支付状态为成功且未在7天内发生全额退款的订单"],
  "dims": "城市、产品线、渠道"
}
```

字段说明：
- `id`：按 `references/06-metric-spec-writing-guide.md` 第 1 节的编号规则生成（域前缀_作用域_序号）
- `type`：原子指标 / 派生指标 / 复合指标，判断逻辑见 `references/02-metric-classification-and-naming.md` 第 2 节
- `status`：三选一——`normalized`（已规范化，无冲突）、`conflict`（检测到冲突，需人工确认，必须配 `conflict_note`）、`new`（盘点过程中发现业务上明显缺失、建议补充的指标，本身企业还没有）
- `analysis` / `rules`：对应八字段模板里的"分析意义"和"业务场景简述"，数组形式，一条一句话，具体写法见 `references/06-metric-spec-writing-guide.md` 第 3 节的五类边界检查清单

## 4. 处理流程（六步）

1. **提取原始条目**：按第 2 节方法把所有候选指标列出来，此时不用管重复和规范，先求全。
2. **聚类去重**：把描述相似的条目聚在一起。判断"是同一个指标"还是"同名不同义"的线索：口径描述（分子分母/统计范围）是否一致、数据来源表是否相同、典型数值量级是否吻合。描述完全一致 → 合并为一条，在 `rules` 里注明"曾用名：XX（来自XX报表）"；名字相同但描述冲突 → 保留为两条，`status` 设为 `conflict`，`conflict_note` 写清楚两边具体差异（参考 `assets/html-templates/metric-audit-table.html` 里 `pay_success_rate` 的示例写法）。
3. **分类打标**：按三段式分类判断每条是原子/派生/复合指标，归入合适的数据域（先看企业是否已有数据域划分，没有的话参照 `references/02-metric-classification-and-naming.md` 或 `references/01-industry-case-studies.md` 里的行业惯例先给出一版划分建议）。
4. **命名与编号**：中文名尽量保留业务方熟悉的叫法（除非明显不规范），英文名和编号按 `references/06-metric-spec-writing-guide.md` 生成，域前缀不确定时可以现场设计一套（3-4 位字母），并在交付物里说明这套前缀的含义。
5. **分级**：结合 `references/02-metric-classification-and-naming.md` 第 4-5 节和 `references/03-governance-process-and-roles.md`，给出资产等级和安全等级的建议值——这一步通常需要问用户几个判断性问题（这个指标是否进公司级看板、是否涉及敏感信息），不要自己瞎猜分级。
6. **质量自查**：交付前检查——`id` 有没有重复、每条 `conflict` 状态是否都写清楚了冲突原因、有没有明显还没处理完的重复条目、`type` 分类是否有和描述矛盾的地方（比如描述里出现了"XX/YY"这种比率结构却被标成了原子指标）。

## 5. 输出：生成 HTML 交互台账

默认交付形式是复制 `assets/html-templates/metric-audit-table.html` 到工作目录，做两处替换：
1. 把 `<script>` 里的 `META` 对象换成企业真实信息（公司/业务线名称、生成日期、数据来源说明——来源说明建议写"原始条目 N 条，规范化后 M 条"这种具体数字，比空泛描述更有说服力）。
2. 把 `METRICS` 数组换成第 4 节流程产出的真实数据（保留数据结构，逐条替换即可，示例数据可以整体删除）。

替换完成后用 `create_file` 落盘到 `/mnt/user-data/outputs/`，再 `present_files` 交付给用户。这个文件本身是完全自包含的（数据内嵌、无外部依赖），用户可以直接用浏览器打开，也可以直接分享给同事，不需要额外部署。

## 6. 备选输出：Excel

如果用户明确要 Excel（比如要在企业内部走审批流程、需要多人协同编辑批注），改用 xlsx skill 生成工作簿，建议至少包含三个 sheet：
- **全量清单**：对应 `METRICS` 全部字段，一行一条指标
- **待确认冲突**：只筛 `status=conflict` 的条目，突出显示冲突说明，方便业务方逐条拍板
- **按数据域视图**：按 `domain` 分组，每个数据域一个区块，方便各业务团队只看自己相关的部分

生成 Excel 前务必先 view `/mnt/skills/public/xlsx/SKILL.md`，按其中的格式规范操作（不要自己随手拼 openpyxl 代码）。

## 7. 和其他模式的衔接

这一步产出的数据是整个 skill 里价值最高的资产——把 `METRICS` 数组（或对应的 Excel 全量清单）保留下来，可以：
- 直接作为模式二（`references/08-metric-extension-method.md`）向导工具的"导入指标库"数据源，让新增指标查重生效
- 直接作为模式三（`references/09-analytical-framework-library.md`）搭建分析框架时"挂载"到框架节点上的指标来源

如果用户只是想单独跑模式一，不需要考虑后续衔接，正常交付即可。
