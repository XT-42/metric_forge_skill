# 模式二：新增维度/指标方法论与流程工具

对应 skill 的第二个实战能力——不是处理存量，而是给企业一套"以后业务方想加新指标/新维度时该怎么走流程"的方法论，交付三件套：方法论文档、决策流程框架图、配套的 HTML 申请向导工具（`assets/html-templates/metric-intake-wizard.html`）。

## 1. 触发场景

用户说"以后业务方总是自己乱加指标，想定一套规范流程"、"帮我们做一个新增指标的申请机制"、"业务想加个新维度，应该怎么走流程"，进入这个工作流。和模式一的区别：模式一处理"已经存在的乱"，模式二解决"以后不再乱"。

## 2. 交付物一：方法论文档

内容骨架直接复用 `references/03-governance-process-and-roles.md`（治理流程与角色）和 `references/02-metric-classification-and-naming.md`（分类命名规范）、`references/06-metric-spec-writing-guide.md`（边界规则怎么写），但**改写文风**——03/02/06 是写给数据团队内部看的规范文档，这里要产出一份写给**业务方/申请人**看的"新手指南"，语言要更口语化、少术语，重点讲清楚：
- 什么情况下应该申请新指标，什么情况下应该先查一下是不是已经有了（不要一上来就讲编号规则，先讲"为什么要克制"）
- 提交申请前要想清楚哪几个问题（可以直接照抄 `metric-intake-wizard.html` 里五步的问题清单）
- 提交之后大概多久能有结果、谁会审批、审批标准是什么（对应 `references/03-governance-process-and-roles.md` 第 2-3 节的角色设计，按用户企业实际情况替换角色名称）

篇幅不用长，一份能让业务方 5 分钟读完、知道该做什么的文档就够了；技术细节（编号规则、分级标准）放在附录，不要堆在正文。

## 3. 交付物二：决策流程框架图

用 Visualizer 画一张流程图，把"提出需求 → 查重 → 判断类型 → 定义草稿 → 审批 → 上线"这条路径可视化，对应 `references/03-governance-process-and-roles.md` 第 2 节的六环节。**这张图和模式三的"分析指标体系框架图"是完全不同的两回事**，不要混淆：这里画的是"一个新指标从提出到上线要走哪几步"（流程图/泳道图性质），模式三画的是"业务逻辑怎么拆解成一棵指标树"（业务框架性质）。如果用户希望这张流程图也做成可保存的文件而不只是对话内展示，可以在 Visualizer 生成后另外用 HTML/SVG 或 PPTX 出一版静态文件。

## 4. 交付物三：HTML 申请向导工具

复制 `assets/html-templates/metric-intake-wizard.html` 交付即可，这个工具是完全通用的，一般不需要大改，但有两处需要按企业情况定制：

### 4.1 数据域下拉选项
工具第一步的 `<select id="s1_domain">` 里内置了几个默认数据域（交易域/用户域/内容域/服务域/流量域/员工域）。如果企业的数据域划分不同（比如模式一盘点时已经确定了一套企业专属的数据域），需要同步修改：
1. `<select id="s1_domain">` 里的 `<option>` 列表
2. `<script>` 里的 `DOMAIN_PREFIX` 字典，为每个新数据域配一个 3-4 位字母前缀（编号规则见 `references/06-metric-spec-writing-guide.md` 第 1 节），保证后续生成的编号前缀和企业实际编号体系一致

### 4.2 导入指标库做实时查重
工具顶部有一个"导入现有指标库"的文件上传入口，接受的 JSON 结构就是 `references/07-audit-and-standardize-workflow.md` 第 3 节定义的共享指标数据结构数组。如果企业已经跑过模式一，直接把模式一 HTML 里 `METRICS` 数组的内容导出成一个独立的 `.json` 文件给到用户，让他们在使用向导工具时上传这个文件，第二步的查重就会自动生效（按字符重叠度做相似度打分，不是精确匹配，所以还是需要人工看一眼排名靠前的候选项）。

如果企业还没跑过模式一，或者不方便整理成 JSON，向导工具会自动降级为"人工确认模式"——不报错、不强制要求导入，只是把查重责任交给使用者自己搜索确认，这是刻意的设计，保证模式二可以独立于模式一使用。

## 5. 关于"这个向导工具的定位"

需要跟用户讲清楚一点预期管理：这个 HTML 工具生成的是**草稿**，不是最终定稿——它能帮申请人把"要不要新建、大概是什么类型、编号大概长什么样"这几件事想清楚，最后一步导出的 JSON/文本仍然需要人工审批（对应 `references/03-governance-process-and-roles.md` 里的"数据管家审批"环节）才能真正入库。工具本身不连接任何数据库或审批系统，纯粹是本地浏览器运行的辅助填表工具——这也是为什么它能做成一个可以直接分享给任何公司用的通用文件，不需要额外部署。

## 6. 常见追加需求

- **要求向导支持团队协作/多人同时用**：说明这超出了"自包含 HTML 文件"的能力边界（没有后端、没有共享存储），如果企业需要这个能力，建议转向 `references/04-metric-platform-architecture.md` 和 `references/05-tool-design-checklist.md` 描述的正式指标平台/CRUD 工具方向，这已经不是"轻量流程工具"能解决的问题了，需要明确告知用户边界。
- **要求向导记住历史提交记录**：同上，静态 HTML 没有持久化能力；如果只是当次会话内需要，可以引导使用"下载草稿"功能自行保存多份 JSON。
