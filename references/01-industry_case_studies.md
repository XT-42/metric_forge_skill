# 指标规范化与指标平台搭建

## 这个 skill 解决什么问题

几乎所有做到一定规模的公司都会撞上同一堵墙：指标散落在几十张报表和几个分析平台里，"支付成功率"在这个部门和那个部门口径不一样，一张新报表要重新写一遍 SQL，出了问题不知道该找谁。这不是某一家公司的特例——阿里、字节、快手、美团、滴滴、盒马、腾讯都在各自的发展阶段撞过这堵墙，也都沉淀出了成熟的方法论。这个 skill 把这些方法论抽象成一套可以直接套用的工作流程，不管用户是要从零梳理指标体系、写一份指标命名规范，还是要设计一个指标管理平台/CRUD 工具，都从这里开始。

**核心心法**（来自快手案例，也是所有大厂方案的共同内核）：
- **一处生产，全局复用**（避免重复建表）
- **一处管理，全局引用**（避免定义和应用分离、改了不生效）
- **一处服务，全局调用**（避免每个平台各写一套取数逻辑）

指标治理做不好往往不是技术问题，而是"动力不足"——建了指标字典没人愿意维护，因为它只是一份约等于 Wiki 的文档，改了定义也不会在下游生效。所以贯穿整个 skill 的一条主线是：**规范必须落地成平台能力，而不是停留在文档里**，否则治理动力会随时间衰减。

## 完整工作流程

这是阿里 OneData、快手 OneMetric+OneService 等方法论共有的骨架，按顺序推进：

### 第一步：业务调研与数据域划分
先搞清楚业务，不要上来就建表。把业务划分成几个相对独立的**数据域**（如快手的直播/短视频/电商/商业化，滴滴的司机/安全/体验/城市），每个数据域内部再抽象出**业务过程**（下单、支付、退款这类不可再拆分的业务活动事件）。这一步做得好坏直接决定后面会不会返工——数据域划分错了，指标会散落在多个域里找不到归属。

### 第二步：建模设计
基于业务过程做维度建模（事实表+维表），确定：
- 原子指标（不可再拆分的度量，如"下单数"）
- 时间周期 + 修饰词/维度 → 派生指标（如"最近7天-手机品类-下单数"）
- 复合指标（多个原子/派生指标四则运算得出，如转化率、客单价）

细节和模型类型（单例/星型/雪花/星座）见 `references/04-metric-platform-architecture.md`。

### 第三步：制定规范
在建模的同时或之后，制定命名规范、词根库、分级规范（数据资产等级/维度等级/安全等级）。**这一步最容易被低估，但决定了体系能不能长期维持一致性**——字节跳动的案例证明，光靠人工维护文档格式不统一、更新不及时，必须有词根库这种强制约束机制。详见 `references/02-metric-classification-and-naming.md`。

### 第四步：设计治理流程与角色
明确"谁能新增指标、谁审批、谁负责维护口径"。业界通行的模式是业务方提需求、数据人员（分析师/数据BP）定义口径、数据管家审批授权、数据开发落地。缺了流程保障机制，指标的准确性就无法保证。详见 `references/03-governance-process-and-roles.md`。

### 第五步：平台化落地
把前四步的成果变成系统能力而不是文档：元数据管理（指标/维度/表/数据集）、模型构建与搜索、查询引擎（DSL→SQL翻译、执行计划、二次计算）、统一服务层。这是"动力问题"的根本解法——平台强制口径复用，业务方不需要额外动力也会用对指标。详见 `references/04-metric-platform-architecture.md`。

### 第六步：工具化与一致性运营
落地指标字典/CRUD 工具（字段设计参考 `references/05-tool-design-checklist.md`），并建立指标一致性检测机制（横向对齐：同层级不同应用间比对；纵向对齐：DWD→DWS→Topic→APP 逐层比对；例行+实时两种检测频率）。

| 字节跳动（火山引擎） | DataLeap + DataWind | 词根管理消除一词多义；数据 BP 与分析师协同维护口径；口径透传到看板 | 指标 100% 覆盖，数据 oncall 下降 40%+ |
| 美团 | 指标平台（自动语义+增强计算） | 星型/雪花/星座模型自动关联；指标血缘树；智能物化+查询降级策略 | "定义即研发"，百万级查询、成功率 99.9%+ |
| 滴滴 | 数据梦工厂 + 数易 + 资产管理平台 | 主题域抽象（司机/安全/体验/城市）；DataRank 六维健康分驱动治理 | 治理五方向：成本/安全/质量/模型/价值 |
| 盒马（阿里体系） | DataWorks + 严格分层规范 | ADS 面向业务不面向开发；DWS 必须承载指标；DWD 字段不可有二义性 | 分层职责边界极其清晰 |
| 腾讯 | 欧拉平台 t-Metric | DataOps + Headless BI；配置驱动生产；指标应用血缘可追溯 | 建、管、查、用一体化 |
| 58同城/赶集集团 | 核心数据指标白皮书 | 统一编号体系（域前缀+作用域+序号）；八字段定义模板；业务场景简述穷尽边界规则 | 纯文档化治理也能做到高完备度 |

## 常见误区（写方案前先避开）

1. **把指标字典当 Wiki 用**：只能看不能管，定义和应用分离，改了口径不会全局生效——这是快手案例明确指出的"指标管理动力不足"的根因。方案里一定要有"一处修改、全局生效"的机制设计，哪怕第一期只是人工同步流程，也要写清楚谁负责同步。
2. **只做技术分层不做业务规范**：ODS/DWD/DWS/ADS 分层是必要条件不是充分条件。盒马案例强调每一层要有清晰职责（比如 DWS 必须是指标的物理载体），光有分层没有语义约束，照样会乱。
3. **重建设轻运营**：字节案例里"重复管理、指标泛滥"的教训说明，指标平台上线只是起点，后续的词根维护、一致性检测、指标下线机制同样重要，不要在方案里漏掉运营环节。
4. **过度设计一步到位**：美团、腾讯这类平台的自动语义、智能物化能力都是在指标规模到万级/十万级之后才需要的。如果用户公司体量不大，直接照搬全套架构会过度工程化——先用简化版跑通"一处定义、一处管理"的核心逻辑，量级上来了再演进。
5. **只关注技术架构，不设计角色和审批流**：平台再强大，没人负责审批新指标、没人维护业务口径，照样会退化成新一轮的野蛮生长。角色设计（数据管家/数据BP等）和技术架构同等重要。

## 交付物建议

根据用户需要的深度，可以产出：
- 指标规范文档（命名规范、分级标准、词根库初稿）——直接写 Markdown 或 Word（用 docx skill）
- 指标治理流程图 + 角色职责说明——可以用 Visualizer 画流程图
- 指标平台技术架构方案——分层架构图 + 关键设计决策说明
- 指标字典/白皮书——见 `templates/metric-dictionary-template.csv`（含编号、八字段定义、口径变体示例），可直接导入 Excel 使用（用 xlsx skill 转换）；字段设计逻辑和撰写方法见 `references/06-metric-spec-writing-guide.md`
- 指标 CRUD 工具的功能/字段设计说明——供研发直接排期开发

产出前先确认用户要的是"方案/文档"还是"能跑的工具原型"，两者的深度和形式差别很大，不要默认往重了做。
