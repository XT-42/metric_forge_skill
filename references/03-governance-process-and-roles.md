# 指标管理流程与角色设计

## 1. 为什么流程比工具更容易被忽略

很多团队上来就想做一个"指标管理平台"，把精力全部投入在系统功能上，但快手案例明确指出问题的根源之一是"无体系化流程保障机制，数据准确性无法保障"——工具只是流程的载体，如果流程本身没设计好（谁能新增、谁审批、口径谁负责），再好的工具也只是把混乱从线下文档搬到了线上系统。所以流程设计应该先于或至少同步于工具设计。

## 2. 指标全生命周期流程（通用范式）

综合快手、字节跳动两家的实践，指标从提出到消费的生命周期可以归纳为六个环节：

```
业务人员提出需求 → 数据人员查重+定义口径 → 数据管家审批/授权
   → 数据开发绑表/设定数据集 → 构建分析产品/发布 → 业务人员消费（看数/读数）
```

### 环节详解

1. **提出需求**（业务人员：产品/运营）：业务方提出想要什么指标，通常是从一个业务问题出发（"我想知道最近大促的转化率"），而不是直接提技术需求。

2. **查重与定义口径**（数据人员：分析师/数据产品/数据BP）：这一步是防止重复建设的关键防线——先在指标字典里检索是否已有满足需求的指标，没有才进入新建流程。新建时需要把业务需求拆解为原子指标 + 时间周期 + 修饰词的标准结构（字节跳动案例的做法），并明确业务口径（这个指标业务上到底代表什么）。

3. **审批/授权**（数据管家）：数据管家角色专门负责审批新指标定义、授权访问权限，是质量关卡而不是橡皮图章——审批时应该检查：是否真的没有可复用的现有指标？口径定义是否清晰无歧义？分级是否合理？

4. **技术开发**（数据开发）：绑定物理表，设定口径对应的数据集（过滤条件、聚合方式等技术口径），完成指标的物理生产逻辑。

5. **构建分析产品/发布**（数据产品）：把指标接入到具体的报表、看板、API 等应用形态，让业务方能实际用起来。

6. **消费**（业务人员：产品/运营）：看数、读数、基于数据做业务决策。这一步应该能直接看到指标口径说明（口径透传），不需要额外找人解释。

流程整体由"规范/流程"和"数据资产标准化管理规范"两条主线贯穿约束——也就是说，每一步都不是随意执行的，而是有明确的规范文档作为依据（比如"查重"这一步依据的是指标命名和分类规范）。

## 3. 角色设计

一个可持续运转的指标治理体系需要清晰的角色分工，不能全部压在一个"数据团队"身上。参考快手和字节跳动两种不同的组织模式：

### 快手模式：内容团队 / 工具团队 / 产品团队三角协同
- **内容团队**：制定流程规范、执行规范流程——偏"治理规则的制定者和执行监督者"。
- **工具团队**：沉淀规范流程为工具能力，提升开发/服务/管理效率——偏"平台研发"。
- **产品团队**：构建数据服务矩阵——偏"面向业务的产品化"。

三个团队互相协同（内容团队定规则→工具团队落地成系统能力→产品团队包装成业务可用的产品→反馈给内容团队优化规则），形成闭环而不是单向传递。

### 字节跳动模式：数据 BP 制
数据 BP（Business Partner）常驻业务侧，深度参与业务需求，同时对接平台能力。相比"纯中台制"（容易脱离业务、自嗨）和"纯 BU 制"（重复造轮子），数据 BP 制的优势是杠杆率高——BP 背靠强大的平台工具和团队支持，能快速响应业务变化，同时把跨业务线积累的经验沉淀为平台方法论。

### 两种模式如何选
- 如果业务线之间差异大、需求变化快、需要贴身服务 → 偏向字节跳动的数据 BP 模式，投入更多"人"的角色去理解业务。
- 如果业务相对标准化、更看重规模化复用和长期规范沉淀 → 偏向快手的三角团队模式，投入更多在"规则+工具"的系统化建设。
- 大部分公司实际是两者的混合：核心通用能力走中台化建设，个性化强的业务线配备类似 BP 的对接人。

### 最小角色集（小团队适用）
如果团队规模不足以拆出三个团队或专职 BP，至少要明确以下三个职责由谁承担（可以是同一个人身兼多职，但职责边界要清楚）：
- **谁负责业务口径**（这个指标业务上是什么意思）—— 通常是分析师或产品。
- **谁负责技术口径**（这个指标技术上怎么算出来）—— 通常是数据开发/数仓工程师。
- **谁负责审批新增/变更**（防止重复建设和口径漂移）—— 哪怕只是一个人一周花半天做这件事，也比完全没人把关要好。

## 4. 一致性保障机制

光有流程约束新增指标还不够，存量指标也会随时间产生不一致（比如上游表结构变了、某个环节的加工逻辑被悄悄改过）。快手案例给出的思路是横向 + 纵向两个维度的对齐检测：

- **横向对齐**：同一层级下，不同应用（APP1...APPN）之间、不同主题（Topic1...TopicN）之间比对同一个指标的取值是否一致。
- **纵向对齐**：沿着数据链路 DWD → DWS → Topic → APP 逐层比对，定位不一致是在哪一层引入的。

检测频率上区分两种：
- **例行一致性检测**：定期（如每日）批量跑一遍比对逻辑，覆盖面广但有延迟。
- **实时一致性检测**：数据产出即触发检测，发现问题响应更快，但通常只能覆盖核心指标（成本考虑）。

设计检测机制时的实用建议：不需要一开始就对所有指标做实时检测，可以按第 3 节里提到的资产分级（A1/A2/A3）分配检测强度——A1 级指标上实时检测，A2/A3 级用例行检测即可。

## 5. 变更管理：解决"改了不生效"的根本问题

快手案例点名的核心痛点是"定义管理与应用使用分离，无法一处变更，全局生效"。这个问题在文档化管理阶段几乎无解——文档改了，用文档手抄 SQL 的下游系统不会自动跟着变。解法必须落到平台层面：

- 指标定义作为唯一权威数据源（Single Source of Truth），下游系统（报表、API、看板）都通过统一服务层查询指标，而不是各自复制一份计算逻辑。
- 变更前先查指标应用血缘（腾讯欧拉案例的能力），评估这次变更会影响哪些下游应用，通知相关方。
- 对 A1/A2 级别的核心指标，变更应该走审批流程而不是直接修改；对 A3 级或个人临时指标可以放宽。

这也是为什么第五步"平台化落地"（见架构参考文档）是整个 skill 里最重要的一步——流程设计得再好，如果最终没有一个统一服务层承接，"改了不生效"的问题依然无解。
