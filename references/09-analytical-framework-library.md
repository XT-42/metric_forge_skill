# 模式三：分析指标体系框架搭建（面向分析师）

对应 skill 的第三个实战能力——不是罗列指标（模式一干的事），也不是定新增流程（模式二干的事），而是把企业历史指标组织成一套"能看懂业务逻辑"的分析框架，帮分析师建立"这个业务域该怎么用指标讲清楚"的框架性理解。交付形式默认是自包含 HTML/SVG 框架图（`assets/html-templates/framework-diagram.html`）。

## 1. 触发场景

用户说"帮我们搭一套 XX 业务的分析指标体系"、"想给分析师一个框架，看数据不要只盯单个指标"、"帮我理一下这个业务域的指标应该怎么分层"，进入这个工作流。判断标准：如果用户要的是"一张能讲清楚业务逻辑的图"，是模式三；如果要的是"一份能查的指标清单"，是模式一。两者经常配合使用（模式一先把存量指标理清楚，模式三再把这些指标"挂"到业务框架上），但产出物性质不同。

## 2. 框架骨架库：四种经典范式

拿到一个业务域后，先判断适合用哪种骨架，而不是每次都从零设计框架结构。四种骨架各有适用场景：

### 2.1 北极星指标树（North Star Metric Tree）
**结构**：根节点是一个北极星指标（能代表业务终极健康度的单一指标），向下拆成若干"策略层"节点（提升北极星指标要靠哪几条路径），策略层下面挂具体的"度量层"指标（衡量每条路径做得好不好）。
**适用场景**：业务目标相对单一清晰的场景——交易类（GMV/成交额）、订阅类（付费用户数/续费率）、内容类（内容消费时长）都适合。
**对应模板**：`assets/html-templates/framework-diagram.html` 默认演示的就是这种结构（`level` 字段用 `north_star` / `strategy` / `metric` 三级）。

### 2.2 AARRR 海盗指标漏斗
**结构**：Acquisition（获取）→ Activation（激活）→ Retention（留存）→ Referral（推荐）→ Revenue（收入），五个阶段依次排列，每个阶段挂对应的转化率和规模指标。
**适用场景**：增长团队视角的用户生命周期分析，尤其适合 C 端产品、订阅制业务、需要拆解"用户从哪来、怎么留下来、怎么花钱"的场景。
**渲染方式**：用 `framework-diagram.html` 的树形结构表达会显得别扭（AARRR 本质是线性漏斗不是树），建议改成横向的阶段卡片布局——可以复制模板后把 `.tree` 相关 CSS 换成简单的 flex 横排卡片，每张卡片代表一个阶段，卡片内部列出该阶段的指标（用同样的 `status: existing/gap` 逻辑标注是否已有对应指标）。

### 2.3 OSM（目标-策略-度量）+ UJM（用户旅程地图）
**结构**：横向是用户旅程的各个阶段（比如"发现-决策-使用-复购"），纵向是每个阶段对应的业务目标（Objective）、达成目标的策略（Strategy）、衡量策略效果的度量指标（Measure），形成一个矩阵。
**适用场景**：需要同时讲清楚"业务想做什么"和"用户实际怎么走"两条线的场景，比较适合产品/运营侧主导的分析框架搭建，尤其是多阶段、多触点的复杂产品。
**渲染方式**：这是矩阵结构，不适合用树形模板表达，建议用一张 HTML 表格（行=旅程阶段，列=目标/策略/度量三栏）呈现，比强行套树形图更清楚。

### 2.4 杜邦分解式框架
**结构**：从一个总指标出发，逐层做乘除分解，直到分解到可以直接归因到某个业务动作的底层指标（经典案例是 ROE = 净利率 × 资产周转率 × 权益乘数）。
**适用场景**：财务、经营效率类分析，或者任何"总指标 = 若干子指标相乘/相除"关系清晰的场景（比如 GMV = 流量 × 转化率 × 客单价 就是一种简化的杜邦分解）。
**渲染方式**：`framework-diagram.html` 的树形结构天然适合表达这种分解关系，把 `level` 语义从"策略层"换成"分解层"即可，节点的 `meta` 字段可以直接写分解公式片段。

### 2.5 怎么选、怎么组合
不需要死板地只用一种——常见的实操方式是"北极星指标树打骨架，某个策略层节点内部用杜邦分解式细化，涉及用户生命周期的部分单独配一张 AARRR 图"。选择时问自己：这个业务域有没有一个大家公认的终极目标指标？有 → 北极星树打底；主要诉求是理解用户从哪来到哪去 → AARRR；需要同时讲清楚业务目标和用户路径 → OSM+UJM；总指标能明确拆解成乘除关系 → 杜邦分解。

## 3. 填充方法：把存量指标"挂"到框架节点上

拿到骨架结构后，逐节点判断企业现有指标（理想情况下是模式一盘点产出的 `METRICS` 数组）里有没有能匹配这个节点的指标：
1. **语义匹配**：对比节点描述（这个节点在讲什么业务问题）和指标的 `analysis` 字段（这个指标衡量什么），重叠度高的匹配上，设 `status: "existing"`，`meta` 字段填指标编号。
2. **识别缺口**：某个节点在业务逻辑上明显需要一个指标支撑，但存量清单里找不到匹配项，设 `status: "gap"`，这是这份框架图最有价值的产出之一——它不只是把已有指标摆个好看的图，而是**主动指出"业务逻辑上这里应该有数但现在没有"**。
3. **不要为了填满而牵强匹配**：如果某个节点确实没有合适的存量指标，宁可标成缺口，也不要硬把一个关系不大的指标塞进去——牵强匹配会让整张框架图失去指导意义。

缺口清单是这份交付物里分析师最应该重点看的部分——`framework-diagram.html` 模板底部自带一个"缺口清单"区块，会自动遍历框架树收集所有 `status: gap` 的节点并列出来，可以直接作为后续模式二（新增指标）工作的输入待办清单。

## 4. 输出：生成框架图 HTML

复制 `assets/html-templates/framework-diagram.html`，把 `<script>` 里的 `FRAMEWORK` 对象换成真实业务域的框架结构（骨架选型见第 2 节，填充方法见第 3 节），`title`/`subtitle` 换成实际业务域名称。落盘到 `/mnt/user-data/outputs/`，用 `present_files` 交付。这个文件同样是自包含的，且内置了打印/导出 PDF 按钮，方便分析师需要的时候直接打印或存成 PDF 分享。

## 5. 给分析师的解读指南（建议附在交付说明里）

交付这张图时，建议一并向分析师说明怎么用它：
- **根节点/顶层**代表这个业务域最终要对什么结果负责，任何单个指标的分析最终都应该能追溯到这里，不要孤立看某个二级指标。
- **实线/已有指标节点**是现在就能拿数据分析的部分。
- **虚线/缺口节点**不是"不重要"，而是"业务逻辑上重要但数据能力还没跟上"，是团队下阶段建设指标的优先级参考，不是画完就完事的装饰。
- 这张图应该是活的——业务变化、新指标上线后，缺口会被填满，也可能出现新的缺口，建议定期（比如每季度）用模式一重新盘点一遍存量指标，再回来更新这张图，而不是画一次就永久使用。
