# 指标分类、分级与命名规范

## 1. 基础概念（先对齐语言，再谈规范）

写任何规范文档之前，先确保业务方和数据团队对以下两个词的理解是一致的——这是快手案例里放在最开头讲的基础概念，看似简单但极容易被跳过，跳过了后面所有规范都建立在流沙上：

- **指标**：对业务事件行为的度量，基本以数量值表示。例如：点击数、曝光数、支付金额。
- **维度**：用来反映业务事件的属性，是观察指标的角度。例如：性别、年龄、城市、商品类目。

以及两个建模概念：
- **业务过程**：企业的业务活动事件，如下单、支付、退款，是不可再拆分的行为事件。
- **数据域**：从业务角度对数据做总体归类和划分，是业务过程或维度的抽象集合（如用户域、交易域、内容域）。

## 2. 指标的三段式分类（行业标准做法）

这套分类在阿里 OneData、快手 OneMetric、字节 DataLeap 里都是核心概念，直接采用，不需要另外发明分类体系：

| 类型 | 定义 | 示例 |
|---|---|---|
| **原子指标** | 基于某一业务过程的、不可再拆分的度量，具有明确业务含义 | 支付金额、下单数、播放量 |
| **派生指标（衍生指标）** | 原子指标 + 统计周期 + 修饰词/维度 三要素组合而成 | 最近30天 - 华东区 - 支付金额；本周 - 母婴品类 - 支付订单数 |
| **复合指标** | 对原子/派生指标做四则运算等计算得出，不直接来自某一次业务过程 | 转化率 = 支付人数 / 访问人数；客单价 = 支付金额 / 支付人数 |

设计指标字典的字段结构时，"指标类型"应该是第一个必填字段，因为它决定了后续要填哪些其他字段（原子指标要填聚合方式和过滤条件；派生指标要额外关联统计周期和修饰词；复合指标要填计算公式和依赖的成分指标）。

### 一个容易踩的坑
不要把"复合指标"和"派生指标"搞混——派生指标是同一个原子指标在不同时间/维度切片下的取值，依然是"同一件事"的度量；复合指标是把不同的事情（如访问和支付）通过运算组合成一个新概念（转化率），本质上是新指标，需要单独定义计算口径，不能简单地当作某个原子指标的"变体"来管理。

## 3. 维度分类

维度也需要分级管理，不是所有维度都同等重要。参考快手的三级维度等级：

| 维度等级 | 划分标准 | 研发要求 |
|---|---|---|
| S1 核心维度 | 高频使用、跨业务通用的维度 | 必须在公共维表（CDM 层）中唯一定义，不允许各团队各自维护一份 |
| S2 常用维度 | 较常使用但不是全局核心 | 同样要求在公共维表中唯一定义 |
| S3 扩展维度 | 特定场景使用的长尾维度 | 无强制要求，允许业务方在应用层灵活扩展 |

核心和常用维度强制唯一定义的意义在于：如果"城市"这个维度在 10 张维表里各有一份、口径还可能不一样（有的按注册城市、有的按当前定位城市），任何跨表分析都会出问题。把 S1/S2 维度收敛到公共维表，是避免这类问题最有效的手段。

## 4. 资产分级：不是所有指标都值得同等对待

给指标分级的意义在于把有限的治理资源（人工审核、监控告警、SLA 保障）优先投入到最重要的指标上。参考快手的三级模型，可以直接套用或按自己公司的组织结构调整层级数量：

| 资产等级 | 划分标准 | 典型承载物 |
|---|---|---|
| A1 | 公司经营核心指标 | 公司核心日报、管理看板 |
| A2 | 部门核心指标 | 部门核心日报、部门管理看板 |
| A3 | 部门日常运营指标 | 部门数据报表 |

分级之后可以配套差异化的治理强度：A1 级指标要求双人审核变更、必须配置数据质量监控告警；A3 级指标可以简化为单人审核、无强制监控。不要对所有指标一刀切用同一套审批流程，那样会导致 A1 级指标审核不够严谨、A3 级指标又太重导致没人愿意走流程。

## 5. 安全分级

指标背后的数据可能涉及不同的安全敏感度，需要单独分级并配合权限体系。参考快手的四级安全等级：

| 安全等级 | 划分标准 |
|---|---|
| C1 | 公共数据 |
| C2 | 内部数据 |
| C3 | 机密数据 |
| C4 | 绝密数据 |

安全等级应该独立于资产等级维护——一个 A3 级的部门运营指标完全可能涉及 C3 级的机密数据（比如涉及未公开的定价策略）；反过来一个 A1 级的公司核心指标也可能是 C1 级公开数据（比如公开披露的 GMV）。两套分级正交存在，权限系统按安全等级控制谁能看到，按资产等级控制谁能改。

## 6. 命名规范与词根管理

### 为什么需要词根库
字节跳动（幸福里）案例里明确指出：录入指标过程中经常出现"一个中文名称对应多个英文名称"或"同一个英文名称在不同业务线下有不同中文含义"的问题——这就是常说的"同名不同义、同义不同名"。解决方式不是靠人工 review 发现问题再改，而是**前置**：录入新指标前，先在词根库里检查要用的关键字是否已经存在，存在就必须复用已有词根，不允许另起一个新词。

### 词根库的最小可行设计
词根库本质是一张受控词表，建议至少包含以下几类词根：

- **修饰词根**（时间/范围类）：如 `1d`（当日）、`7d`（近7天）、`30d`（近30天）、`mtd`（月至今）
- **动作词根**（对应业务过程）：如 `click`（点击）、`expose`（曝光）、`pay`（支付）、`refund`（退款）
- **对象词根**（业务实体）：如 `user`、`order`、`item`、`shop`
- **统计方式词根**：如 `cnt`（计数）、`amt`（金额）、`rate`（比率）、`avg`（平均）

命名时按 `[修饰词根_]对象词根_动作词根_统计方式词根` 的顺序拼接，如 `7d_user_pay_amt`（近7天用户支付金额）。具体顺序约定可以按公司习惯调整，但一旦定下就要写进规范文档并在指标录入工具里做校验，不能人工凭记忆遵守。

### 命名规范检查清单
写一份指标命名规范文档时，建议至少覆盖以下条目：
- 中文名称格式：是否允许使用行业黑话/内部代号？是否要求包含统计周期？
- 英文字段名格式：全小写+下划线、还是驼峰？缩写是否要求在词根库里注册？
- 是否允许指标重名（不同数据域下同名不同义是否被允许，还是强制全局唯一）？
- 别名机制：同一个指标是否允许挂多个业务别名（不同部门习惯叫法不同），别名和主名的关系如何维护？
- 废弃指标如何命名/标记（避免物理删除导致下游血缘断裂，通常用状态字段标记"已废弃"而不是删记录）？

## 7. 常见问题与解法对照表

| 问题现象 | 根因 | 对应解法 |
|---|---|---|
| 同名不同义（同一个名字，两个部门算法不一样） | 指标定义分散在多处，没有统一注册入口 | 强制"新增指标前先查重"的流程 + 唯一的指标注册中心 |
| 同义不同词（同一件事，不同英文字段名） | 缺少受控词根库，命名全靠个人习惯 | 词根库前置校验（字节跳动案例的核心解法） |
| 指标口径变了，下游不知道 | 定义与应用分离，改了定义不会通知/生效到下游 | 指标应用血缘 + 变更通知机制（腾讯欧拉案例） |
| 报表里的指标看不懂怎么算出来的 | 口径信息只存在数据团队内部文档，没有透传给消费方 | 口径透传到看板/产品页面（字节跳动案例） |
| 指标越建越多，没人清楚哪些还在用 | 缺少下线机制和使用热度追踪 | 指标应用血缘 + 定期使用率巡检，低使用率指标标记待下线 |
