# 指标规范文档撰写指南：编号体系、定义模板与口径规则

前面几份参考文档讲的是"怎么设计治理流程和平台架构"，这份讲的是更具体的一层：**指标字典/指标白皮书这份文档本身应该怎么写**。内容主要拆解自 58同城/赶集集团《核心数据指标白皮书》——一份完全靠人工撰写、没有依赖任何平台工具、但完备度极高的指标文档范例，证明"文档化治理"只要做扎实，本身就有很强的生命力，不是平台上线前的将就方案。

这份指南解决的问题是：拿到一堆业务指标需求，怎么落成一份别人能看懂、能查、能长期维护的规范文档，以及这份文档最终应该长什么样（对应用户常问的"最终输出的指标字典是什么样子"）。

## 1. 指标编号体系设计

在给指标起名字之前，先设计编号规则——编号是不随改名而变化的稳定主键，名字迟早会有人建议"改得更清楚一点"，编号不会。

推荐的编号结构（三段式）：

```
[域前缀]_[作用域]_[序号]
例：INCM_G_00030001
```

- **域前缀**：3-4 位字母，代表这个指标属于哪个业务/数据域。例如：INCM（收入 Income）、MCHT（客户 Merchant）、EMEF（员工效能 Employee Efficiency）、TFIC（流量 Traffic）、INFO（信息/内容 Info）、RCRT（招聘 Recruit）。设计时先把公司的指标域盘一遍（通常就是第一步"数据域划分"的产出），再给每个域分配唯一前缀，写进规范文档里公示，不要临时起。
- **作用域标记**：1 位字母，区分这个指标的适用范围。常见用法是 G=集团级/全局通用指标，P=某条业务线专属指标。这个标记能让人一眼看出"这个指标是不是我这条业务线能直接套用的"，避免误用只在某个业务线成立的指标。
- **序号**：定长数字（如 8 位），建议**分段留白**而不是从 1 连续编到底——比如同一父指标下的子指标共享前几位，如 `00030000` 是父指标"销售开通业绩"，`00030001`～`00030005` 是它拆解出的五个子类型（会员业绩、信息服务业绩等）。这样光看编号就能看出指标之间的父子关系，不用另外去查血缘表。

编号一旦分配，**不允许复用**——指标下线后编号作废保留，不能给新指标复用旧编号，否则历史报表引用会串数据。

## 2. 指标定义模板：八字段版

比"逻辑定义+物理定义"的两段式（见 `references/05-tool-design-checklist.md`）更完整的写法是固定八个字段，适合作为对外发布的"指标白皮书"文档格式（区别于内部指标管理工具的数据库字段设计，这里是给人看的文档排版）：

| 字段 | 说明 | 容易被省略但很重要的原因 |
|---|---|---|
| 编号 | 见第 1 节 | 跨系统引用的稳定主键 |
| 指标名称 | 中文名 | — |
| 英文名称 | 英文名/字段名 | 供系统间接口对齐 |
| 指标定义 | 一句话说清楚这个指标度量什么 | 必须是完整句子，不能只写"XX的数量"这种同义反复 |
| 分析意义 | 这个指标用来支持什么判断/决策，通常编号列出 2-3 条 | **最容易被跳过，但最该写**——强制回答"为什么需要它"，能过滤掉相当一部分"为了有而有"的冗余指标申请 |
| 业务场景简述 | 详细的计算规则，穷尽边界情况，通常编号列出 | 全文档信息密度最高的部分，见第 3 节 |
| 备注 | 可用维度、特殊说明、相关指标提示 | 避免遗漏拓展信息 |

一个完整条目的骨架（示例为占位内容，实际撰写时替换为真实业务规则）：

```
编号：MCHT_G_00060000
指标名称：推广会员数
英文名称：Membership Paying Members
指标定义：统计期间内，使用付费推广产品进行推广的会员客户数
分析意义：
  1、衡量会员客户中主动做推广投入的规模，反映会员活跃付费意愿
  2、结合推广会员数饱和度，评估各城市会员的推广渗透空间
业务场景简述：
  1、某些特定业务类型（如团购）不纳入统计范围
  2、进行推广的非会员客户不纳入统计范围
  3、同一会员在统计周期内多次推广，仅统计一次
备注：可按现金推广和优惠推广分别统计
```

## 3. 业务场景简述：五类边界规则检查清单

这是整份文档里最容易写得潦草、但对下游最关键的部分——一句模糊的定义在实际数据里必然撞上边界情况（退款怎么算、渠道怎么算、新客怎么定义），如果文档没写清楚，最终变成"每个engineer按自己理解各写一套"，又回到了"同名不同义"的老问题。写业务场景简述时，逐条对照以下五类检查清单，看自己的指标是否涉及、是否已经写清楚：

1. **异常/正常状态的不同处理**：这个事件有没有"正常完成"和"异常中止"两种路径，两种路径对指标计算的影响是否一样？（例如：正常退款 vs 服务开始前的非正常退款，对已计入业绩的扣减方式完全不同——前者要从已计入业绩里扣除，后者视为"这笔业绩从未发生过"，两者不能用同一条规则处理。）
2. **不同来源/渠道的口径差异**：同一件事通过不同渠道发生时，统计口径是否需要统一？（例如：渠道业务和直销业务如果分别以折扣后/折扣前金额计入，会导致渠道折扣力度变化时业绩产生"虚假波动"，所以通常统一用折扣前金额，避免被折扣策略污染。）
3. **时间窗口类定义的具体数值**：凡是涉及"新客/老客""首次/复购""到期前后"这类概念，是否给出了明确的天数/月数阈值？（例如："到期前后 N 个月内购买"才算续费，否则算新签——N 的具体取值必须写进文档，不能让不同团队自行假设。）
4. **组合/拆分场景的统计边界**：这个指标是否存在"打包在别的产品里一起卖"的情况，打包部分要不要单独统计？（例如：会员套餐里搭售的余额，是算进"会员业绩"还是单独算"打包余额业绩"？两者不能混算，否则总量会被重复计算。）
5. **资金/数量流向的方向性**：涉及账户余额、库存这类"存量"概念时，是否明确区分了"正向流入"（真正的新增）和"内部流转"（账户间转账、退款回退等不产生净增量的移动）？（例如：账户充值只统计真正的外部资金流入，账户间互转不计入充值，否则同一笔钱会在两个指标里被重复计算一次。）

写作建议：每条边界规则用编号列出，一条规则只讲一件事，避免把多个条件揉在一个长句里。规则里出现的具体数值（天数、比例、金额阈值）要显式写出，不要用"最近"“一段时间”这类模糊词。

## 4. 多口径变体命名：基础名 + 括注限定词

同一个业务概念，经常需要按不同的统计范围拆出好几个变体——比如衡量"人效"，到底该不该把管理岗、支持岗算进分母，不同使用场景的答案不一样。推荐的命名方式是**基础指标名 + 括注限定词**，而不是每个变体起一个完全不同的名字：

```
销售人效                    （只算一线销售，最窄口径）
销售（满岗）人效             （在"只算一线"基础上，只统计满勤的）
销售（含销管）人效           （一线销售 + 销售管理岗）
销售（含支持人员）人效       （一线销售 + 销售管理岗 + 支持岗，最宽口径）
```

这样命名的好处：
- 使用方能通过名字直接判断口径宽窄，不需要打开定义文档才知道区别。
- 检索时搜"销售人效"能一次性看到所有变体，便于对比选择，而不会因为名字完全不同而漏检索到某个变体。
- 新增变体时，只需要在括注里加限定词，不需要重新设计一套命名规则。

反面案例（不建议）：给"销售（含支持人员）人效"起一个跟"销售人效"完全不相关的名字（比如"团队综合效能"），检索和对比时会大大增加认知成本。

## 5. 派生指标族：把复用的复合公式正式定义成一族指标

如果发现同一个计算模板反复套用在不同的基础指标上，不要让每个使用方临时手写公式，而应该把这个模板正式定义成一族有独立编号的派生指标。典型例子是"区域可挖掘潜力"类指标，模板固定为：

```
(某城市X指标 / 该城市流量) / (全国X指标 / 全国流量) × 100%
```

只要 X 是一个有业务价值的规模型指标（营收、订单量、活跃用户数……），都可以套用这个模板生成一个"X饱和度"指标，且这类饱和度指标的分析意义也高度一致（>100% 代表该城市该指标已经好于全国平均水平、挖掘空间较小；<100% 代表尚有提升空间），可以直接复用同一套分析意义文案模板。

批量生产这类指标族时的实操建议：
- 给这个模板本身起一个族名（如"XX饱和度"），并在文档里用一段话统一说明模板的计算逻辑和分析意义，每个具体变体的条目里只需要写清楚"X 具体是什么指标"，不用每条都重复整套公式解释。
- 编号上可以让同族指标共享某种可识别的规律（比如都在父指标编号后追加固定的偏移量），方便按族检索。
- 识别"可以批量化"的信号：当你发现自己在给第三个不同的基础指标手写同一个公式时，就是该把它转正为指标族模板的时候。

## 6. 文档治理头模板

指标字典/白皮书作为一份文档，本身也需要版本管理，哪怕暂时没有平台承载。最低成本的做法是在文档开头加一页治理信息：

```
文档名称：XX公司核心数据指标白皮书
文件状态：[ ] 征求意见稿   [ ] 正式发布
作者：XX部门
责任部门：XX部门（负责长期维护，不是写完就完事）
审批人：
审批日期：

修订历史：
版本号 | 日期 | 修改人 | 审阅人 | 摘要
V1.0   | ...  | ...   | ...   | 首次发布
V1.1   | ...  | ...   | ...   | 拆分XX指标为AB两个口径，补充XX规则
```

这个模板即使团队完全没有指标平台，也能立刻落地，是"从没人管的野文档"迈向"有版本、有责任人的规范文档"成本最低的一步——比直接跳去做系统开发现实得多，建议任何指标治理项目的第一个交付物就是这样一份带治理头的文档，系统能力可以后续再补。

## 7. 从零撰写一条指标定义：练习步骤

拿到一个新的指标需求时，按以下顺序把这份指南的各节内容串起来使用：

1. 确认这个指标属于哪个数据域，取得域前缀，在该域下按序分配编号（第 1 节）。
2. 判断这是原子指标、派生指标还是复合指标（见 `references/02-metric-classification-and-naming.md` 第 2 节），并检查是否已存在相似指标（避免重复定义）。
3. 按八字段模板起草定义（第 2 节），"分析意义"字段强制自问"这个指标要支撑什么决策"，答不出来说明这个指标可能不必要。
4. 对照五类边界检查清单（第 3 节），逐条自问是否涉及、是否写清楚了具体规则和数值。
5. 如果这个指标是某个已有基础指标的口径变体，用"基础名+括注限定词"命名（第 4 节）；如果计算模板已经在其他指标上用过，考虑转正为指标族（第 5 节）。
6. 提交前确认文档本身的版本记录已更新（第 6 节）。

这六步走完，产出的指标定义条目基本可以直接进入评审流程，不需要来回补细节。
