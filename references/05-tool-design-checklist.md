# 指标字典 / 指标 CRUD 工具设计清单

本文给研发指标管理工具（哪怕是最小可行版本）时用作字段清单和交互设计参考，主要提炼自快手 OneMetric 元数据管理模块的表单设计（分类信息 → 业务信息 → 技术信息三步表单），并补充通用工具设计要点。

## 1. 表单分三步走，而不是一个大表单

快手的指标新增表单分三个 Tab：**分类信息 → 业务信息 → 技术信息**。这个顺序设计是有意义的：先让填表人确定"这是个什么"（分类、归属数据域），再填"这代表什么"（业务口径，通常由分析师/业务方填），最后填"怎么算出来"（技术口径，由数据开发填）。分开的好处是同一张表单可以由不同角色分阶段填写，不需要一个人同时具备业务理解和 SQL 能力。

## 2. 核心字段清单

### 逻辑定义信息（业务口径，业务信息 Tab）
| 字段 | 说明 | 是否必填 |
|---|---|---|
| 指标名称 | 中文名，如"搜索栏用户日活占比" | 必填 |
| 英文名称 | 对应字段名，如 `search_user_in_active_user_ra` | 必填，需通过词根库校验 |
| 指标别名 | 支持添加多个，不同部门习惯叫法 | 选填 |
| 资产等级 | A1/A2/A3（见分类分级参考文档） | 必填 |
| 安全等级 | C1-C4 | 必填 |
| 业务负责人 | 负责维护业务口径的人 | 必填 |
| 权限负责人 | 负责审批访问权限的人 | 必填 |
| 技术负责人 | 负责维护技术口径的人 | 必填 |
| 指标单位类型 | 不设置 / 金额类 / 时长类等 | 必填 |
| 业务口径 | 用一句话描述业务含义，如"进行搜索的用户数占登录app的用户数的比率" | 必填 |
| 标签设置 | 便于检索分类 | 选填 |

### 物理定义信息（技术口径，技术信息 Tab）
| 字段 | 说明 |
|---|---|
| 聚合类型 | 如 COUNT_DISTINCT、SUM、AVG 等 |
| 过滤条件 | 如 `is_spam = 1`，用于剔除脏数据 |
| 关联表/字段 | 该指标由哪张物理表的哪个字段加工而来 |

### 数据集（模型层，用于查询时组装）
| 字段 | 说明 |
|---|---|
| 数据集名称 | |
| 描述信息 | |
| 已选指标 | 该数据集包含哪些指标 |
| 已选维度 | 该数据集包含哪些维度 |
| 高级配置 | 数据表信息、数据源等 |

### 分类信息（分类信息 Tab，第一步填写）
| 字段 | 说明 |
|---|---|
| 所属数据域 | 决定归属和后续查重范围 |
| 业务过程 | 关联到具体的业务活动事件 |
| 指标类型 | 原子指标 / 派生指标 / 复合指标（决定后续要展示哪些额外字段，如派生指标要额外填统计周期和修饰词，复合指标要填计算公式和依赖的成分指标） |
| 操作人 | 自动记录，不需要手填 |
| 状态 | 草稿箱 / 待审核 / 已发布 / 已下线 |

## 3. 派生/复合指标的额外字段

指标类型选了"派生指标"或"复合指标"后，表单应该动态展示额外字段，不要把所有类型的字段都堆在一张表单里：

- **派生指标额外字段**：关联的原子指标、统计周期（1d/7d/30d/mtd 等）、修饰词/限定维度
- **复合指标额外字段**：计算公式（引用其他指标的表达式，如 `[支付人数] / [访问人数]`）、依赖的成分指标列表（用于自动生成血缘关系）

## 4. 状态流转与审批

最小可行的状态机：`草稿 → 待审核 → 已发布 → 已下线`，配合：
- 草稿 → 待审核：填表人提交，系统自动做词根库校验和查重检索（检索到相似指标应提示，而不是直接拒绝——可能确实是需要新建的近似但不同的指标）。
- 待审核 → 已发布：数据管家（或按分级设定的审批人）审核通过。A1 级建议双人审核，A2/A3 可单人审核。
- 已发布 → 已下线：不建议物理删除记录，用状态字段标记，保留血缘信息供历史追溯。下线前应检查指标应用血缘，确认没有存量下游依赖，或已通知相关方迁移。

## 5. 查重与推荐

新增指标前的查重是防止"重复管理、指标泛滥"的第一道关卡（也是最容易被跳过的一步，因为搜索体验不好时用户会懒得查，直接新建）。查重体验的最低要求：
- 按中文名/英文名/别名模糊检索。
- 检索结果展示已有指标的业务口径摘要，让填表人能快速判断是否是自己想要的指标，而不是只看名字。
- 如果确认没有可复用的，系统应该允许直接从"相似指标"一键复制大部分字段（数据域、指标类型等），减少重新填写的成本——查重环节越顺畅，大家才会真的愿意先查再建。

## 6. 血缘与影响面分析（进阶功能，非必须但强烈建议尽早规划）

即使第一期不做完整的自动血缘解析，也建议在数据模型设计阶段就把"这个指标依赖哪些其他指标/字段"和"这个指标被哪些下游应用使用"这两类关系记录下来（哪怕是手工登记），因为：
- 上游血缘（指标依赖谁）：支撑复合/派生指标的自动生产、变更影响面分析（改了原子指标，哪些派生/复合指标要跟着变）。
- 下游血缘（谁在用这个指标）：支撑下线评估、变更通知（腾讯欧拉案例的核心能力）。

这类关系一旦积累多了再补录成本很高，建议从工具上线第一天就把"依赖哪些指标"和"被哪些应用引用"设计成表单的一部分，即便前期是手工填写而非自动解析。

## 7. 与查询/服务层的接口设计

指标字典工具不应该是一个孤立的元数据管理系统，最终要能被查询服务消费。设计工具时预留：
- 每个已发布指标有唯一的指标 ID/编码，供查询服务、报表工具、API 通过 ID 引用，而不是通过容易变化的中文名称引用。
- 指标定义变更时提供 Webhook/事件通知机制（或至少版本号+更新时间字段），供下游系统感知变更、决定是否需要刷新缓存。
- 提供只读的查询 API（不只是管理界面），让报表工具、看板可以直接拉取指标的口径说明用于展示（对应"口径透传"能力）。

## 8. MVP 范围建议

如果时间/人力有限，第一期只做以下功能也能覆盖大部分痛点：
1. 指标新增/编辑表单（分类+业务口径两个 Tab 即可，技术口径可以先用一个自由文本框记录 SQL 片段，不做结构化）
2. 按名称/别名的查重检索
3. 简单的状态流转（草稿/已发布/已下线）+ 单人审核
4. 指标列表页可以按数据域、资产等级筛选
5. 只读查询 API，供其他系统读取指标口径

不建议第一期就做：自动模型关联（星型/雪花/星座）、智能物化、自动血缘解析——这些都是指标规模上量之后才需要的能力，过早投入会拖慢上线节奏，见架构参考文档第 8 节的搭建优先级建议。
